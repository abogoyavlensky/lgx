# Custom `lg` runtimes for Go deps

When a project declares `:go/*` coords, lgx cannot run it on the `lg`
from `PATH`: the Go packages have to be linked into the binary. So lgx
generates a small Go module, builds an `lg` from it, and caches the
result. Cross-compilation rides the same machinery: a target-platform
`lg` for `lgx build --target`/`--all` is the same generated module
built with `GOOS`/`GOARCH` set, even when the coord set is empty. This
note covers what goes in that cache, when it is rebuilt, and what
breaks.

## Cache layout

```
$LGX_HOME/runtimes/<hash>/
  lg                     the built binary
  src/
    go.mod               module lgx.local/runtime
    main.go              os.Exit(cli.Main("<version>", "<commit>"))
    lginterop-tool       host-built binding generator (interop builds)
    interop/
      doc.go             placeholder + blank imports
      interop_<alias>.go generated by cmd/lginterop
```

The binary *is* `lg` - same flags, same REPL, same resolver, same `-b`.
`pkg/cli.Main` takes the version and commit it should report, so the
built runtime (and any binary bundled from it) answers `lg -v` with the
let-go it actually contains: the version Go selected, read back from
the tidied `go.mod`. Under `LGX_LETGO_REPLACE` there is no released
version to name, so the pair is `("dev", "replace")`.

## What the hash covers

`runtime-hash` folds together:

- the let-go reference: the `:lg-version` pin, or `replace:<abs-path>`
  when `LGX_LETGO_REPLACE` is set. A *mutable* pin - a branch or tag
  like `"main"` - is first resolved to its pseudo-version
  (`go list -m let-go@<ref>`, one network call per invocation), so the
  cache key names the commit, not the name pointing at it; a semver or
  full sha is hashed literally and stays offline on cache hits.
- every Go coord, canonicalized as `lib|version|interop|local` and
  sorted, so declaration order does not matter
- the target platform (`target|<os>/<arch>`) for a cross-build. A
  native build adds nothing, so pre-target caches stay valid; the
  host's own platform named explicitly still hashes differently, since
  that binary is built with `CGO_ENABLED=0`.

Two projects declaring the same set share one build. Changing anything
lands on a different path rather than invalidating one in place, so
switching a version back and forth costs one build each, not one per
switch. A multi-platform release grows the cache by one ~25 MB entry
per platform (plus the host runtime for a Go-deps project);
`lgx clean --runtimes` reclaims them.

What the hash does **not** cover is the *contents* of a `:go/local`
directory or an `LGX_LETGO_REPLACE` checkout. Hashing a working tree
would mean walking it on every command.

## Rebuild policy

- `<hash>/lg` exists and no working tree is involved: use it, run
  nothing.
- Any `:go/local` coord, or `LGX_LETGO_REPLACE` set: always re-run the
  build steps. `go build` is incremental, so a no-op rebuild is under a
  second. This is the price of not hashing working trees.
- `LGX_LG` set by the user: no runtime is built at all. lgx warns that
  the Go namespaces will not resolve and gets out of the way.

## The build steps

With cwd `src/` (passed as `go -C <dir>`, so no path goes through shell
quoting):

1. `go get github.com/nooga/let-go@<ref>` - skipped under
   `LGX_LETGO_REPLACE`, whose replace directive `go get` cannot express
2. `go get <pkg>@<version>` for each `:go/version` coord
3. `go mod tidy`
4. re-render `main.go` from the let-go version Go actually selected
   (`go list -m -f {{.Version}}`, offline) - MVS may have upgraded past
   the pin, and a sha pin only gets its pseudo-version here
5. when any coord has `:go/interop`: build `cmd/lginterop` for the
   *host*, then run it with the *target's* `GOOS`/`GOARCH`/cgo setting
   in the environment (see the gotcha below)
6. `go build -o ../lg .`, with `GOOS=<os> GOARCH=<arch> CGO_ENABLED=0`
   for a cross target

Each failure prints the toolchain's own output and exits 1. `--verbose`
traces every command.

### Why `go get` and not a `require` line

A coord symbol is a Go *package* path, and that is not always a
*module* path: `golang.org/x/crypto/ssh` lives in module
`golang.org/x/crypto`. lgx has no way to know where the split falls, so
it never writes `require` lines for external coords - `go get` resolves
the owning module itself.

let-go gets the same treatment: the pinned case writes no `require`
line, and `go get let-go@<ref>` means `:lg-version` can be a semver
(`"1.11.1"`, prefixed with `v`), a branch (`"main"`), or a full commit
sha, all passed through as-is. `LGX_LETGO_REPLACE` is the exception:
its go.mod keeps the `v0.0.0` placeholder require plus the `replace`.

`:go/local` coords are the other exception: their module path is read
out of the target's own `go.mod`, which is why a `:go/local` target
must be a Go module.

## Cross-compilation

`ensure-runtime!` takes an optional `{:os :arch}` target. Only the
final `go build` (and the lginterop scan) see it; `go get` and `tidy`
are platform-independent and run host-side. `GOOS`/`GOARCH` reach the
subprocess as environment variables via an `env(1)` prefix, since the
toolchain is invoked with `go -C` rather than through a shell.

`CGO_ENABLED=0` is forced for every cross target: a cgo dependency
cannot cross-compile without a target C toolchain, and lgx saying
"pure-Go drivers only" beats a Go linker error. `modernc.org/sqlite` is
pure Go, so the sqlite stack cross-builds cleanly.

Measured on a linux/arm64 host (2026-08-23): a fully cold stock build
(empty module and build cache) 10.8s; warm module, cold build cache
9.3s; a no-op rebuild 0.5s; a cache hit 0ms. With the sqlite driver
linked in, a cold build cache took 15.3s.

`GOOS=windows` does not work yet: let-go's `pkg/rt/term.go` uses
`golang.org/x/sys/unix` unguarded, so the final build fails upstream
(see [`docs/issues/windows-build-unix-only-term.md`](../issues/windows-build-unix-only-term.md)).
Every unix-family target verified so far (linux/amd64, linux/arm64,
darwin/arm64) builds.

## Gotchas

**The interop placeholder's blank imports are load-bearing.**
`main.go` imports `lgx.local/runtime/interop`, but nothing imports the
*wrapped* packages until `lginterop` has run - and `go mod tidy` runs
first. Without a blank import of each wrapped package in
`interop/doc.go`, tidy prunes the requirement `go get` just added and
`lginterop` then fails with `the scanned package must be resolvable
from the current directory's module`. This is a chicken-and-egg the
placeholder exists to break.

**`lginterop` must scan the *target's* API, so it is built then run,
never `go run`.** The go/types source importer selects files and
symbols by `GOOS`/`GOARCH`, read from the environment when the process
starts. `go run` with `GOOS=darwin` on a linux host would try to build
a darwin tool it cannot execute; a plain `go run` would scan the host
API and emit host-only symbols (linux `syscall` bindings reference
`EpollCreate`, which does not exist on darwin) that fail the target
build. So lgx builds `lginterop-tool` for the host with no target env,
then runs it under the target's `GOOS`/`GOARCH` plus the same cgo
setting the final build uses.

**`-opaque-structs` is not optional.** Without it `lginterop` flattens
struct types into field-only Records, and every method call fails with
`no method Query on record sql/DB`. Every interesting Go API is used
through its methods, so lgx always passes the flag.

**A `/v2` module needs a matching placeholder version.** Go rejects
`require example.com/mod/v2 v0.0.0` outright, replacement or not. The
placeholder version is derived from the module path's major suffix.

**Paths with spaces must be quoted.** go.mod's directive grammar splits
on whitespace, so an unquoted `=> /tmp/sp ace` parses as a path plus a
bogus version.

**Methods are not first-class values in let-go.** `(.Query db q p1 p2)`
works with literal arguments, but a wrapper holding its parameters in a
vector cannot spread them - there is no `(apply .Query ...)`. The fix
belongs in a Go shim that takes a slice and spreads it.

**`[]any` needs a let-go carrying the boxing-symmetry fix.** On older
let-go versions, `vm.BoxValue` walks a slice by its *static* element
type, so every element of a `[]any` reaches let-go as an opaque
`vm.Boxed` comparing equal to nothing, and a let-go vector containing
`nil` fails to convert to `[]any` going the other way. The fix ("make
[]any cross the Go/let-go boundary as native values", on
`integration/go-interop`, unreleased as of 2026-08-23) boxes
interface-typed elements by their dynamic type and lets `nil` elements
through, so shims can use plain `[]any` in both directions. Against a
let-go without it, fall back to `[]vm.Value` plus explicit
`vm.ToLetGo`/`Unbox` conversion on both sides.

## `LGX_LETGO_REPLACE`

Points the generated `go.mod` at a let-go working tree:

```
LGX_LETGO_REPLACE=/path/to/let-go lgx run
```

It emits `require github.com/nooga/let-go v0.0.0` plus a `replace`, and
forces a rebuild on every command. This is how the pipeline is tested
against an unreleased let-go - `pkg/cli` and `cmd/lginterop -out-pkg`
have to exist in the version being linked, so a pinned `:lg-version`
only works once a release carries them.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `go` is not on PATH | Preflight; install Go. Cross-builds need it even with no Go deps |
| `declares Go deps but no :lg-version` / `cross-compiling ... :lg-version` | The runtime links let-go itself; pin it. Required for any cross-build |
| `does not contain package .../pkg/cli` | The pinned let-go predates out-of-tree interop; use `LGX_LETGO_REPLACE` |
| `the scanned package must be resolvable` | The placeholder's blank imports are missing or stale |
| `no method X on record ...` | Built without `-opaque-structs` |
| `alias "log" is also used by ...` | Two `:go/interop` packages share a last path segment; `lginterop` writes one file per alias |
| Namespaces missing from a bundled binary | `-b` used a stock `lg` as its base; lgx injects `-bundle-base` unless you passed your own |
| `undefined: unix.SIGWINCH ...` on a windows target | let-go does not build for `GOOS=windows` yet (upstream issue) |
| C sources / `cgo` errors on a cross target | The dep needs cgo; cross-builds run `CGO_ENABLED=0`, so use a pure-Go driver |

To force a cold rebuild, delete the leaf
(`rm -rf $LGX_HOME/runtimes/<hash>/`), or drop the whole cache with
`lgx clean --runtimes` (`--dry-run` first reports what would go).
