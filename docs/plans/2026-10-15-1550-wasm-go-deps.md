# `:target :wasm` with project Go deps Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let `lgx build` with `:target :wasm` link the project's `:go/*` deps into the browser app, using let-go's `lg -w -w-module <dir> -import <pkg>` (nooga/let-go#998, phases 1-2).

**Tech Stack:** let-go (`.lg`), `lg -w` with `-w-module`/`-import` (let-go #1016, #1037; on `main` after v1.13.0), the Go toolchain, lgx's runtime builder (`lgx/gobuild.lg`), the lgx unit suite (`bin/lgx test`), `tests/e2e.sh`.

**Origin:** lgx issue #61, phase 3 of nooga/let-go#998. The first phase (`docs/plans/2026-10-01-1303-wasm-build-target.md`) shipped `:target :wasm` without Go deps. Resources in the WASM app (nooga/let-go#999) stay out of scope.

---

## Design

### What changes for users

A `:target :wasm` project may now declare `:go/*` deps (direct or transitive) under `:lg-runtime :built`:

```clojure
{:main "main.lg"
 :lg-runtime :built
 :lg-version "<a let-go with -w-module>"
 :deps {github.com/spf13/cast {:go/version "v1.7.1" :go/interop "cast"}
        hash/crc32 {:go/interop "crc32"}}
 :targets {:bin {:target :wasm :out "dist/web"}}}
```

`lgx build` writes the same web directory as before, and the app can `(:require [cast])`.

Unchanged:
- A `:wasm` project with no Go coords keeps the current path exactly: plain `lg -w`, works on lg 1.13.0 and under `:installed`. Its argv stays byte-identical.
- Go coords under `:installed` keep failing in `apply-runtime!` with `installed-go-deps-error`.
- Resources still only warn.

New errors:
- The host runtime's let-go lacks `-w-module` (any release up to 1.13.0): a clear error naming the requirement and the fix (pin `:lg-version` to a let-go that has it).
- A forwarded `-w-module` or `-import` arg: rejected, because lgx sets both from `:deps`.
- A Go dep that does not compile for `js/wasm` (cgo drivers, syscall-heavy packages): fails while lgx builds the js/wasm runtime, under lgx's existing "Building custom lg runtime for js/wasm..." header, with Go's own error.

### Verified facts this design rests on

Checked 2026-10-15 on let-go `main` `1fb38034` (via `LGX_LETGO_REPLACE`), lgx master `a0c9572`, in a scratch project with `github.com/spf13/cast` (`:go/interop`) and `hash/crc32` (`:go/interop`):

- `lgx run` built the runtime at `~/.lgx/runtimes/<hash>/` with `src/` holding `go.mod`, `go.sum`, `main.go`, `interop/` and a leftover `lginterop-tool` binary.
- Copying `src/` (minus `lginterop-tool`) to a scratch dir and running `<runtime>/lg -w web -w-module <copy> -import lgx.local/runtime/interop main.lg` built under `-mod=readonly` with the go.sum lgx produced, unchanged. lg wrote `<copy>/lgprogram/{.lg-generated,imports.go,main.go,program.lgb}`.
- In headless Chromium (`playwright-core` + `chrome-headless-shell`) the page printed the same output as the native run. Without `-import`, it failed with `TypeError: nil is not a function`.
- `GOOS=js GOARCH=wasm CGO_ENABLED=0 go build .` on that module also succeeds (about 30 MB `lg.wasm`), so `ensure-runtime!` with target `{:os "js" :arch "wasm"}` works for portable deps.
- `lg -h` on that runtime lists `-w-module` and `-import`; lg 1.13.0's `-h` lists neither.
- `-w-module` refuses an existing `lgprogram/` without its `.lg-generated` marker and replaces one that has it. It never edits `go.mod`/`go.sum`.
- Generated go.mod `replace` targets (`LGX_LETGO_REPLACE`, `:go/local`) are absolute paths, so the module still resolves after a copy. Task 3 re-verifies this for `:go/local`.

### Approach: two runtimes, a staged module

The app needs two things that can differ:

1. **A host `lg` that compiles the program.** Compiling resolves `(:require ...)`, so the Go namespaces must exist at build time. This is the host runtime `apply-runtime!` already builds under `:built`.
2. **A Go module whose bindings fit js/wasm.** lginterop picks files and symbols by `GOOS`/`GOARCH`, so bindings for the browser must be generated under `js/wasm`. lgx's cross-build path does exactly that: `ensure-runtime!` with target `{:os "js" :arch "wasm"}` builds a separate cached module (its own hash), runs lginterop under the target env with `CGO_ENABLED=0`, and `go build`s it for js/wasm.

`build-wasm!` gets both runtimes and copies the js/wasm runtime's `src/` into a fresh temp dir. It then runs the host `lg` with `-w-module <temp> -import ...` and deletes the temp dir afterwards, whether the build succeeds or fails.

### Key decisions

- **Reuse `ensure-runtime!` for the js/wasm module, binary included.** It gives caching, the `:go/local` content stamp, `:go/replace`, and a target-env lginterop scan for free. The cost is one extra `go build` for js/wasm (a ~30 MB binary nobody runs), paid only on a cache miss. That build also fails early, with an lgx-labeled header, on a dep that cannot compile for js/wasm. A "module only" mode would skip the build but add a second cache state to stamp and test. Not worth it now.
- **Stage into a temp dir, never into the cache.** `lg -w-module` writes `lgprogram/` into the module. The cached `src/` is shared by every project with the same deps, so two concurrent builds would race on it, and a later `go mod tidy` there would see a stale `lgprogram/`. A per-build copy of a few small files avoids both. Go's build cache keeps the rebuild cheap. Copy only `go.mod`, `go.sum`, `main.go` and `interop/` (when present). `lginterop-tool` is a 10+ MB host binary the build never needs.
- **Imports mirror the runtime's `main.go`.** Pass `-import lgx.local/runtime/interop` when any coord has `:go/interop`, and one `-import <pkg>` per link-only external coord (no `:go/interop`). Both lists come from the same predicate `render-main-go` uses, factored into one pure function so the native launcher and the WASM app cannot drift.
- **Capability check by probing `lg -h`, after the host runtime exists.** `:lg-version` can be a tag, a branch or a sha, so version comparison cannot answer "has `-w-module`". The host runtime's `-h` text can. The probe runs only when there are Go coords, after `apply-runtime!` and before the js/wasm runtime build, so an old pin fails before the second (slow) build. Split into a pure `w-module-supported?` on the help text plus a thin impure wrapper.
- **Only Go-coord projects take the new path.** No coords means no `-w-module`. That keeps 1.13.0 and `:installed` working and the existing e2e scenario unchanged.
- **Reject forwarded `-w-module`/`-import`.** lgx owns both. A user value would conflict with the staged module or the import list. Extend `wasm-build-arg-error`.
- **`go` on PATH stays required**, as today (`wasm-go-missing-error`).

### Testing

- Unit (`test/lgx/gobuild_test.lg`): `link-packages`, `wasm-import-args`, `w-module-supported?`, the new error strings, and `wasm-build-arg-error` with forwarded `-w-module`/`-import`. Existing `render-main-go` tests must stay green after the refactor.
- E2E (`tests/e2e.sh`): scenario 168 changes from "Go deps rejected" to cheap, hermetic checks: Go deps under `:installed` still fail before any build, and a forwarded `-import` is rejected. A new gated scenario (`LGX_WASM_E2E=1`) does a real build with a stdlib `:go/interop` coord (`hash/crc32`, no network beyond let-go itself). It asserts the web directory exists, that `lgprogram/` did not land in `$LGX_HOME/runtimes/*/src`, and runs `main.wasm` under node with Go's `wasm_exec.js` (as let-go's own `test/e2e/caller_module_test.go` does), expecting the checksum. Its `:lg-version` comes from `LGX_WASM_E2E_LG_VERSION`, defaulting to let-go `main` sha `1fb38034` until a release carries `-w-module`.
- Manual browser check (Task 8): the playwright-core script from the spike, against the built `examples/` project, before merging.

### Task 4: Wire it into `build-wasm!`

**Files:**
- Modify: `lgx.lg` (`build-wasm!`, around line 837)

- [ ] **Step 1: Replace the Go-deps rejection.** Order inside `build-wasm!`:
  1. Existing arg, shell and main checks (unchanged; the forwarded `-w-module`/`-import` rejection rides in via `wasm-build-arg-error`).
  2. `go-available?` check (unchanged).
  3. `apply-runtime!` (unchanged; returns the host runtime path under `:built`, and fails Go coords under `:installed` itself).
  4. When `(seq go-pairs)`:
     a. Unless `(gobuild/w-module-supported!? host-runtime)`, write `wasm-w-module-error` and exit 1.

  5. Build `args`: wasm flag args, then `["-w-module" staged]` and `wasm-import-args` (when staged), then `forward`, then `["-w" abs-out abs-main]`.
  6. Run `invoke-lg!` in a `try`/`finally` that `syscall/rm-rf`s the staged dir. `os/exit` happens after the `finally` (capture exit first), so cleanup is never skipped.
