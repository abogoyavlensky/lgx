# `.clj` Library Support Implementation Plan

**Status:** lgx-side complete (2026-05-30); waiting on upstream let-go release before the gated e2e scenarios light up and the `vN.N` doc placeholders can be pinned.

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make pure-Clojure libraries that ship `.clj` source files (hiccup, medley, fipp, …) installable and `require`-able through lgx. The lgx-side work pairs with a small upstream let-go patch tracked as `docs/issues/letgo-clj-support.md`.

**Tech Stack:** let-go (`.lg`), bundled lgx CLI, existing namespace resolver in let-go, existing `os/sh` + env wiring in `lgx/runner.lg`, existing test-discovery walk in `lgx/test_runner.lg`.

---

## Design

### What this builds

After this plan lands (plus the corresponding upstream let-go release):

```
project/
  lgx.edn               :deps {hiccup/hiccup {:git/url ... :git/sha ...}}
  src/myapp/main.lg     (require '[hiccup.core :as h])    ;; works
  test/foo_test.clj                                       ;; discovered by `lgx test`
```

`lgx run`, `lgx build`, `lgx test` all spawn `lg` with `LG_READ_CLJ=1` in the environment so `:clj` reader-conditional branches match, in addition to `:lg` and `:default`. Priority between branches is `:lg > :clj > :default`, independent of source order — let-go-native code always wins when present, with `:clj` and `:default` available as fallbacks for libraries authored against JVM Clojure.

### Empirical confirmation of the gap

Renaming `greeter.lg` → `greeter.clj` in the lgx-template-base example today produces:

```
$ lgx --verbose run
+ lg -source-paths /Users/andrew/Projects/lgx-template-base/src main.lg --
error: Can't resolve greeter/greet in this context
  --> main.lg:5:8
   |
 5 |   (prn (greeter/greet "let-go")))
   |        ^^^
```

Renaming the same file to `greeter.cljc` works. So today's let-go resolver loads `.cljc` but not `.clj` — verified against the candidate list in `pkg/resolver/resolver.go::Load`, which ships exactly four candidates per namespace (`<hyphen|underscore><.lg|.cljc>`).

A second, latent gap: let-go's reader conditional matching is **first-match-wins**:

```go
// pkg/compiler/reader.go:1124-1126
isMatch := !found && (key == lgConditionalTag ||
    (matchCljConditional && key == cljConditionalTag) ||
    key == defaultConditionalTag)
```

That `!found` means `#?(:default Z :lg X)` selects `Z`, and once we ship the env-var that turns the `:clj` lens on, `#?(:clj Y :lg X)` would select `Y` — both surprising. The upstream issue includes a priority-based fix so this can't bite users like `tiny-cli` whose `.cljc` files mix `:lg` and `:clj` branches in either order.

### Upstream let-go work (three tiny diffs)

Tracked separately in `docs/issues/letgo-clj-support.md`. Summarized here so the lgx-side work has context:

1. **Resolver: append `.clj` to the candidate list** (`pkg/resolver/resolver.go::Load`). Two extra entries placed **after** the `.cljc` entries so existing collisions resolve identically:

   ```go
   candidates := []string{
       hyphenPath + ".lg",
       underscorePath + ".lg",
       hyphenPath + ".cljc",
       underscorePath + ".cljc",
       hyphenPath + ".clj",       // new
       underscorePath + ".clj",   // new
   }
   ```

2. **Env var wiring: read `LG_READ_CLJ` at startup** and call `compiler.SetMatchCljConditional(true)` when set to a non-empty value. The maintainer's comment at `pkg/compiler/reader.go:1063-1070` already names the env var (as `LETGO_READ_CLJ`); we propose `LG_READ_CLJ` to match the existing `LG_*` prefix used by `LG_BOXARGS_DEBUG` and `LG_PANIC_STACK`.

3. **Reader conditional priority: `:lg > :clj > :default`** regardless of source order. Replaces the current first-match-wins scan with a priority-pick. Eliminates the `:default`-shadows-`:lg` surprise and makes `#?(:clj Y :lg X)` resolve the same as `#?(:lg X :clj Y)`.

### Why `.clj` is appended (not prepended) in the resolver

Strictly additive change. Any namespace that resolved before resolves identically afterwards. `.clj` is only consulted when neither `.lg` nor `.cljc` exists. A library that ships both `foo.cljc` (let-go-safe) and `foo.clj` (JVM-flavored) keeps loading the safe one. No risk to existing projects or to let-go's own conformance baseline.

### Why `LG_READ_CLJ=1` is set unconditionally by lgx

lgx exists to host let-go applications that depend on the Clojure ecosystem. Any project lgx runs is one where the user has chosen to opt into that ecosystem — so the `:clj` lens being on is the right default for *every* lgx-spawned `lg` process. Setting it once in `runner.lg::invoke-lg!` is one line; per-project opt-in would require an `lgx.edn` schema change with no real upside.

The priority-fix upstream change is what makes this safe for let-go-native projects: `:lg` always beats `:clj` when present, so projects like `tiny-cli` keep loading their `:lg` branches regardless of which order the author wrote the conditional.

### Why no `lg --version` detection in lgx

If a user runs lgx against an older `lg` that predates the upstream patch:
- `LG_READ_CLJ=1` is an unread env var — silently ignored.
- `.clj` files still fail with `Can't resolve …` — same behavior as today.
- No regression.

lgx already trusts the user's `lg` (`LGX_LG` env var, no version check). We extend that stance here: document the minimum let-go version in the README and let users encounter the existing error if they're on an older release.

### Coverage matrix

| Comes for free once let-go ships the resolver patch | Needs explicit lgx-side change |
|---|---|
| `(require '[hiccup.core])` from a git-cached dep | `lgx test` discovery walks for `*_test.clj` |
| `:local/root` deps containing `.clj` files | `validate-single-test-file!` accepts `.clj` |
| User's own `src/foo.clj` files | Validation error message includes `.clj` |
| `:deps/root` overrides pointing into `.clj` trees | `runner.lg::invoke-lg!` sets `LG_READ_CLJ=1` |
| Reader-conditional priority in `.cljc` files | Documentation updates |

The left column is the resolver-patch payoff. The right column is the lgx PR.

## Out of scope (YAGNI)

- Per-project or per-dep opt-in for the `:clj` lens (`:lg/read-clj` in `lgx.edn`). The lens is process-global in let-go; lgx flips it for every spawn. Revisit if a user surfaces a concrete need.
- A `lg` CLI flag (`-read-clj`). Env var is sufficient and avoids weaving around `--` in the spawn argv. The maintainer can add the flag later; lgx doesn't need it.
- The cache-mutation rename approach (`.clj` → `.cljc` at install time). Rejected because it doesn't help `:local/root` deps or user-project `src/foo.clj`, mutates the cache away from upstream fidelity, and is fundamentally a workaround for the resolver patch we're shipping anyway.
- `.cljs` extension support. Out of scope; let-go isn't a JS host.
- A `lg --version` check at lgx startup. Doc-only minimum-version note, matching lgx's existing `LGX_LG` stance.
- Bumping any existing `.cljc` files in lgx itself to add `:clj` branches. lgx is a bundled binary; reader conditionals are irrelevant to its own source.
