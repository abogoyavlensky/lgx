# Maven Deps Resolution Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add `:mvn/version` coordinate support to lgx — top-level in lgx.edn and transitively from git deps' deps.edn files — resolved via the grenadine library with an lgx-supplied host effect map.

**Tech Stack:** let-go (.lg), grenadine (pure-Clojure Maven resolver, sha-pinned git dep), shell-outs to `unzip`/`sha1sum`/`shasum`.

---

## Design

### Approach

lgx gains a third coordinate type, `:mvn/version`, alongside `:git/*` and
`:local/root`. Git and local deps stay in the existing breadth-first walk
(`ensure-all!` in `lgx.lg`). Maven coords — whether top-level in the
project's lgx.edn or discovered transitively — are *collected into a pool*
during the walk instead of being resolved in place. After the walk, one
call to grenadine's `install!` resolves the whole Maven subgraph: pom
fetching/parsing (parents, BOMs, property interpolation), transitive graph
walking, version mediation, sha1-verified artifact download, and jar
extraction into per-jar source-root directories. Extracted roots append to
`-source-paths` after git dep paths.

This split is clean because poms can only reference Maven coords — a
Maven dep can never pull the resolution back into git-land.

Grenadine itself is a sha-pinned git dep in lgx's own `lgx.edn`, fetched
by the existing gitlibs machinery (no bootstrap problem: grenadine has
zero dependencies) and AOT-bundled into the lgx binary by the normal
build. Both interpreted and `lg -b`-bundled operation were verified
against grenadine `3dc2f07` during design (full `install!` of integrant
under lg 1.12.2, and a standalone bundle resolving into a fresh cache).

### Why grenadine, and what lgx supplies

Grenadine's core is pure portable Clojure with effects injected through a
"host" map of functions passed as `:host`. lgx supplies that map
(~50 lines) built on let-go primitives:

- `:http-get` → `http/get` (response `:body` is a raw-byte string;
  byte-exact — verified against jar sha1 checksums during design)
- `:read-bytes`/`:write-bytes!` → `slurp`/`spit` (byte-exact);
  `:bytes->utf8`/`:utf8->bytes` → `identity` (strings-as-bytes convention)
- `:digest` → temp file + `sha1sum`/`sha256sum` shell-out, `shasum -a N`
  fallback (macOS); let-go has no SHA natives
- `:extract-jar!` → `unzip -q -o` shell-out into a `.part` dir, marker
  file `.grenadine-complete`, then `mv` into place (mirrors the JVM
  host's atomicity protocol)
- `:byte-count` → `count` (valid because let-go strings are raw Go
  byte strings; guarded by a test assert)
- `:exists?`/`:mkdirs!`/`:atomic-move!`/`:delete!`/`:home-dir`/`:getenv`
  → `file-exists?`, `mkdir`, `os/sh mv -f`, `os/sh rm -f`, `os/getenv`

**Pitfall (verified bug in released lg 1.12.2):** never alias any
namespace as `core` — `(:require [x :as core])` breaks all subsequent
variadic fns. Use `gren`, `mvn`, etc. Fixed on let-go main, but lgx must
stay compatible with the released binary.

### Key decisions

- **Cache at `~/.lgx/mvnlibs`** (grenadine `:local-repo` option), never
  `~/.m2/repository`. lgx-owned lifecycle, mirrors `~/.lgx/gitlibs`,
  no interference with JVM tooling. `GRENADINE_LOCAL_REPOSITORY` is
  deliberately not honored — the location is deterministic.
- **Mediation `:tools-deps`** (grenadine `:mediation` option) — least
  surprise for users coming from deps.edn.
- **Global exclusion `org.clojure/clojure`** (grenadine `:exclusions`
  option) — clojure is the runtime let-go replaces; excluding it also
  transitively removes spec.alpha and core.specs.alpha (they only enter
  via clojure's pom). Verified during design.
- **Explicit `:repos`** passed to grenadine: Clojars then Maven Central.
  A test-only override, `LGX_MVN_REPOS` (comma-separated URLs), lets the
  e2e suite point the bundled CLI at a local fixture server; it is
  undocumented and not part of the public surface. A user-facing
  `:mvn/repos` config (and private-repo auth via env vars) is an
  explicit follow-up, not v1.
- **lgx's own build bootstrap:** `make build` bundles with a raw `lg`
  (`lg -b bin/lgx lgx.lg`), which resolves nothing from `lgx.edn` —
  so once `lgx.lg` requires grenadine, the Makefile must put a
  grenadine checkout on `-source-paths`. A `deps-bootstrap` make target
  clones grenadine into `.deps/grenadine/` (git-ignored) at the sha
  parsed from `lgx.edn` (awk, same pattern as VERSION), and
  build/dev targets pass `-source-paths ".:.deps/grenadine/src"`.
  The `lgx.edn` dep entry remains the single source of truth for the
  pin and also serves `bin/lgx test`/dev flows via the normal gitlibs
  machinery.
- **deps.edn fallback for git deps:** `ensure-all!` currently reads only
  a dep's `lgx.edn` for transitive coords. New behavior: if `lgx.edn` is
  absent, read `deps.edn` top-level `:deps` (aliases ignored).
  `lgx.edn` wins when both exist.
- **Conflicts are first-wins by lib name, in BFS order — in both
  realms.** A pooled mvn coord whose lib name was already resolved as
  git/local is dropped with the existing "already resolved as …
  ignoring …" warning (git realm wins because it is seen first). The
  pool itself dedups the same way: first occurrence of a lib name wins,
  a later differing coord warns and is dropped — identical to the git
  realm's policy. Grenadine's `:tools-deps` mediation applies only
  *inside* the pom walk (transitives of the pooled roots), never to the
  pool entries themselves.
- **No lock file.** Grenadine's lock is consumed in-memory inside
  `install!`; nothing is persisted.
- **Source-path probe heuristic for git deps unchanged** (src/ if
  present, else repo root); deps.edn `:paths` is not read. Non-goal.

### deps.edn coordinate translation

Reading a dep's `deps.edn` produces lgx coord pairs by these rules:

| deps.edn form | translation |
|---|---|
| `{:mvn/version "1.2.3"}` | kept as mvn coord; per-dep `:exclusions` passed through |
| `{:git/url … :git/sha …}` or `:git/tag` | kept as git coord |
| `io.github.X/Y` or `com.github.X/Y` with `:git/sha`/`:git/tag`, no `:git/url` | url inferred: `https://github.com/X/Y` |
| other inferred-url hosts (io.gitlab.*, etc.) | warn and skip |
| `{:local/root …}` | kept; resolved relative to the dep's own directory (matches existing lgx.edn transitive behavior) |
| `org.clojure/clojure` | silently filtered |
| anything else (no recognizable coord) | warn and skip |

### Data flow

```
lgx.edn :deps ──► ensure-all! BFS (git/local as today)
                    │  per dep: coords-at (lgx.edn) else deps-edn-coords-at
                    │  mvn coords → pool (first occurrence per lib name)
                    ▼
              mvn pool ── drop libs already in `seen` (warn) ──►
                    mvn/install-mvn! ── grenadine install!
                    {:host (mvn host map) :local-repo ~/.lgx/mvnlibs
                     :repos [clojars central] :mediation :tools-deps
                     :exclusions ['org.clojure/clojure] :source-roots? true}
                    ▼
              [{:lib … :path <extracted root> :installed? …} …]
                    ▼
        basis paths = project :paths ++ git dep paths ++ mvn roots
```

`install-mvn!` derives its result rows from grenadine's return value: the
`:lock` artifact entries carry coords and jar paths, `:source-roots` are
the per-jar extraction dirs (match to artifacts by jar-path prefix), and
`:fetched` vs `:cached` determines `:installed?`.

### Error handling

- Missing `unzip` binary: preflight check before the grenadine call with
  a clear actionable error (`lgx: 'unzip' is required to install
  :mvn/version deps — install it and retry`), exit 1.
- Grenadine failures (`:grenadine.core/install-failed`, checksum
  mismatch, unresolvable pom): catch ex-info, print the message and the
  failed coordinates without a stack trace, exit 1 — same style as
  `coords-at!` handles `:lgx/invalid-dep-config`.
- Invalid mvn coords in lgx.edn: rejected by the schema with the
  existing config error report.

### Testing strategy

No network in the suite. Integration tests run grenadine against a local
fixture Maven repo served by let-go's `http/serve` from
`tests/fixtures/mvn-repo/` (Maven directory layout, hand-made tiny poms +
jars + `.sha1` files). The fixture repo contains `fixture/lib-a`
(depending on `fixture/lib-b` and `org.clojure/clojure`) and
`fixture/lib-b` — enough to prove pom-driven transitivity and the clojure
exclusion (the fixture server has no clojure artifact, so success proves
exclusion). Unit tests cover the pure parts: schema validation, deps.edn
translation, pool/seen interaction, digest and extract helpers against
real temp files.

Implementation-time verifications (cheap asserts inside tests):
- `count` on a binary string returns bytes, not runes (compare
  `(count (slurp jar))` to the file's byte size) — required for
  `:byte-count`.
- Second `install!` over a warm cache fetches nothing (assert via the
  fixture server's request log / `:cached` result).

### Out of scope (explicit)

- `:mvn/repos` user config + private-repo auth (follow-up; host
  `:http-get` is the designed hook point)
- Persisted lock file
- Reading deps.edn `:paths`/`:aliases`
- S3-backed repos
- Native `os/unzip` and SHA builtins (upstream let-go wishlist)
